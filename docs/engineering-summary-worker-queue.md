# Persistent Worker Queue + Outbound-Call Hardening — Engineering Summary

Addresses the two real production gaps the prior milestone's self-review flagged as next: the ingestion job queue (`api/jobs.py`'s `JobStore` -- single-process, in-memory, one worker thread, state lost on restart) and the complete absence of retry/timeout handling on Pinecone/Postgres calls. Scoped to those two, not the full "production platform" wishlist (worker priority/cancel/pause included since they're cheap once a real queue exists; Prometheus, OpenTelemetry, circuit breakers, and a caching layer were not -- see Explicitly skipped, below).

## What changed

**Persistent, claim-based job queue.** `ingestion_jobs` (already existed in the Supabase schema from a prior milestone, unused) gained `priority`, `payload`, `result`, `available_at`, `heartbeat_at`, `max_retries`, `idempotency_key` columns plus three partial indexes for the claim/reaper query shapes. `PostgresJobRepository` (`storage/repositories/postgres/job_repository.py`) implements a new `JobRepository` protocol (`storage/repositories/base.py`, same Protocol-in-base/Postgres-impl pattern as every other repository in this codebase): `enqueue` (idempotent via a unique `(organization_id, idempotency_key)` index), `claim` (`FOR UPDATE SKIP LOCKED`, ordered by priority then age -- no two workers ever claim the same row), `heartbeat`, `complete`, `fail` (exponential backoff requeue under `max_retries`, else `dead_letter`), `cancel` (queued-only), `reap_stale_claims`, `list_dead_letter`.

**WorkerPool** (`api/jobs.py`) replaces the single-thread `JobStore` *only* when Postgres is configured: N worker threads (`RAG_WORKER_CONCURRENCY`, default 4) each loop claim→process→complete/fail, a per-job heartbeat thread keeps its claim alive while it runs, and a reaper thread requeues any claim whose heartbeat goes stale (`RAG_WORKER_HEARTBEAT_TIMEOUT_S`, default 120s) -- recovering work from a killed/crashed worker without operator intervention. `pause()`/`resume()` and graceful `shutdown()` (stop claiming, join in-flight work up to a deadline) round out what's needed to actually operate this in production. No Postgres: `JobStore` is untouched, still one worker thread -- correct, not a compromise, because the scanning fallback's BM25 index is a full local-pickle rebuild with no incremental-write safety for concurrent workers.

**Why concurrency > 1 is safe now (and wasn't before).** The prior milestone made BM25 postings, dedup, and compliance writes incremental and Postgres-indexed (`PostgresBM25Repository`, `PostgresChunkRepository`, `PostgresComplianceRepository`) -- each ingest only touches its own new rows, no shared full-corpus rebuild in the critical path. That's what makes concurrent workers correct today where they weren't when `JobStore`'s single-worker constraint was written; this milestone is the payoff of that architecture, not a new risk taken on top of it.

**Idempotent submission.** `POST /upload/async` (when Postgres is configured) writes uploaded bytes to `uploads_dir` before enqueueing (payload carries stored paths, not file contents -- jsonb is the wrong place for megabytes of file bytes, and a worker picking the job up after a restart still finds the files on disk), then computes an idempotency key from the sorted content hashes of every file plus the request's metadata fields. A client retrying the same `/upload/async` call after a timeout (never having seen the first 202) gets the existing job id back instead of double-queueing the same files.

**Outbound-call hardening.** `RetryingProxy` (new `rag_hybrid_search/resilience.py`) wraps the Pinecone SDK's `Index` client at its one construction seam (`PineconeConnection.index`'s lazy-init branch) -- every `query`/`upsert`/`fetch`/`delete`/`update`/`list` call across `pinecone_vector_store.py` and `pinecone_chunk_store.py` now retries transiently with full-jitter exponential backoff, without touching either of those files (there was previously *zero* retry/backoff on the Pinecone path, unlike `providers/nvidia.py`'s existing httpx retry loop). `PostgresConnectionPool` now sets `statement_timeout=30s` on every connection it opens -- previously unbounded, meaning a hung query could hold a pool connection (out of a max of 10, shared by every repository and now every worker) indefinitely.

## Repository architecture discipline

`JobRepository` is a Protocol in `storage/repositories/base.py`, `PostgresJobRepository` its only implementation, wired into `Container` by `api/dependencies.py`'s composition root exactly like `DocumentRepository`/`ChunkRepository`/`BM25Repository` before it -- no new one-off module, no special-cased branching outside the existing `if settings.supabase_db_url: ... else: ...` seam that already selects Postgres-vs-scanning for every other repository. `WorkerPool` depends on the `JobRepository` Protocol, never on `psycopg` or SQL.

## Comparison to production ingestion platforms

**Similar:** claim-based queues via `SELECT ... FOR UPDATE SKIP LOCKED` on the primary datastore (rather than standing up Redis/SQS/Celery for a single-region, moderate-throughput ingestion workload) is a well-established, boring pattern -- Postgres-as-queue is what GitHub, Basecamp/Solid Queue, and many others run in production at meaningfully larger scale than this project's. Heartbeat-based crash recovery and exponential-backoff dead-lettering match what Sidekiq/Celery/SQS all do structurally.

**Intentionally different:** OpenAI/Anthropic-scale ingestion platforms run a dedicated broker (SQS, Kafka, a managed queue service) with cross-region durability and much higher throughput ceilings than one Postgres table can give. That's a valid future migration once this Postgres-backed queue's throughput is actually the bottleneck -- and `JobRepository` is exactly the seam a future SQS-backed implementation would slot into without touching `WorkerPool` or the route layer. Standing that up now, with no measured throughput problem to justify it, would be exactly the kind of speculative infrastructure this project's engineering discipline (see CLAUDE.md/ponytail conventions) exists to avoid.

## Explicitly skipped (and why)

- **Prometheus/OpenTelemetry/Grafana.** The existing in-process `Metrics` class is already documented (`api/dependencies.py`) as a deliberate `ponytail:`-flagged simplification, single-instance/portfolio-scale, swap-when-needed. Nothing in this milestone changes that calculus -- there's still one instance, still no cross-instance aggregation need. `WorkerPool`'s state is already fully observable via `GET /jobs/{id}` (status/progress/retry_count) and `GET /jobs/dead-letter/list`; adding a metrics *export* pipeline with no consumer for it would be pure speculative infrastructure.
- **Circuit breakers.** Retry-with-backoff plus a 30s statement timeout covers the actual failure modes present (Pinecone transient errors, a runaway query) without adding a second stateful abstraction (open/half-open/closed) whose main benefit -- protecting a *caller* from a *known-down* dependency -- doesn't apply at this scale (one process, a handful of workers, not a fleet that could each independently hammer a downed Pinecone).
- **Query/retrieval caching layer.** No evidence anywhere in the codebase or its metrics of repeated-identical-query load that a cache would help; retrieval latency's dominant costs (embedding call, Pinecone query, rerank) aren't cacheable across distinct questions anyway. Speculative until a real access pattern shows up.
- **Retrying Postgres writes.** Considered and rejected: `documents`/`chunks` writes are `ON CONFLICT DO UPDATE` upserts (already idempotent), but blindly retrying an arbitrary failed write risks a double-apply on statements that aren't idempotent by construction. Fixed the actual gap (no timeout) without introducing that risk.
- **Full priority/tenancy/multi-region worker fleet.** `priority` is a plain integer column, sufficient for "some uploads matter more" without a scheduler abstraction; no multi-tenant fairness algorithm was built since `default_organization_id` is still effectively single-tenant (unchanged from the prior milestone).

## Self-review

1. **Would this survive many concurrent uploads without architectural redesign?** Yes for the queue itself -- `FOR UPDATE SKIP LOCKED` scales to as many workers as the Postgres connection pool allows (currently `max_size=10`, shared with every other repository; the prior milestone already flagged this as needing tuning once a worker queue landed -- still true, and now the actual knob to tune, `RAG_WORKER_CONCURRENCY` plus pool `max_size`, exists).
2. **Can multiple workers safely run simultaneously?** Yes, verified both by the concurrency test (`test_multiple_workers_process_jobs_concurrently`, asserts actual overlap, not serialization) and by the underlying invariant: every per-job write goes through the incremental, indexed Postgres repositories from the prior milestone, no shared full-corpus mutation in the write path.
3. **Are there remaining O(corpus) operations in this milestone's scope?** No new ones introduced. `PineconeChunkStore._scan_all()`'s existing full-corpus scan/cache (pre-existing, out of this milestone's scope) is unaffected by the retry wrapping -- retries wrap individual `index.*` calls, not scan orchestration.
4. **Are there unnecessary network calls?** No new ones added; retries only fire on actual transient failures (bounded at 4 attempts, full-jitter backoff), not proactively.
5. **Would a Principal Engineer approve this for production?** For this project's actual scale (single-instance Render deployment, moderate document volume) -- yes: it closes the two gaps that were real (job durability, outbound retry/timeout) using patterns proportionate to that scale, and leaves an honest, disclosed list of what a *bigger* deployment would need next rather than building it speculatively.

## Remaining technical debt (disclosed)

- The connection pool's `max_size=10` is still fixed and shared between request-serving repositories and worker threads -- at `RAG_WORKER_CONCURRENCY=4` plus normal request traffic, contention is possible under sustained load. Not a blocker today; the next tuning pass should measure actual pool wait times before raising `max_size` blindly.
- `WorkerPool.shutdown()`'s in-flight-job wait has a fixed deadline (30s default) -- a job mid-embedding-call past that deadline is left running un-joined; its heartbeat protects it from the reaper, but the shutdown call itself returns before it's confirmed finished. True graceful drain (stop, wait unbounded, or forcibly cancel) wasn't built since ingestion isn't preemptible mid-call without deeper changes to `IngestionPipeline`.
- Multi-tenancy is still nominal (`default_organization_id`, unchanged from prior milestones) -- the queue is organization-scoped in its schema (idempotency key, dead-letter listing) but nothing yet creates a second organization in practice.
