# Incremental Indexing Subsystem — Engineering Summary

Implements Problems 1–3 of the storage redesign (incremental BM25, production duplicate detection, indexed compliance metadata) as one cohesive indexing subsystem, built on the repository/DI/Unit-of-Work architecture established in the prior milestone.

## What changed

**Problem 1 — Incremental BM25.** `PostgresBM25Repository` (`storage/repositories/postgres/bm25_repository.py`) writes postings per new chunk (`bm25_postings`, `bm25_doc_stats`) and applies one incremental `UPDATE` to `bm25_corpus_stats` (`total_chunks += N`, `total_length += N`, `avg_doc_length` recomputed from the new totals) — never re-touches existing postings. `search()` scores classic Okapi BM25 entirely in SQL: an indexed postings lookup per query term (`bm25_postings(organization_id, term)`), joined against `bm25_doc_stats` for length normalization. `IndexManager.rebuild_bm25_index()` now passes a **lazy** chunk provider (`self.chunk_store.all`, not `list(self.chunk_store.all())`) to `BM25Repository.rebuild_full()` — the Postgres implementation's `rebuild_full()` is a documented no-op that never calls the provider, so the full-corpus Pinecone scan that used to run on every `rebuild_bm25=True` ingest (the default) simply doesn't happen for this backend. BM25 state is no longer a local pickle file for the Postgres path — the scanning fallback still uses one, but that's an explicit, documented, unchanged behavior for the no-Postgres case.

**Problem 2 — Production duplicate detection.** Exact duplicates: unchanged from the prior milestone (SHA256 `chunk_hash`, unique-indexed). Near-duplicates: `chunks.simhash` (a 64-bit SimHash over word 3-shingles, `storage/repositories/hashing.py`) plus an LSH banding table (`chunk_simhash_bands`, 8 bands × 8 bits) give an *indexed* candidate lookup — `PostgresChunkRepository.find_near_duplicate_candidates()` finds chunks sharing at least one band via `(band_index, band_value) IN (...)`, a fixed 8-pair lookup regardless of corpus size. `IngestionPipeline` now fetches embeddings for *only* those candidates (`ChunkStore.get_many_with_embeddings()`, a targeted Pinecone `fetch()` by known ids) instead of `all_with_embeddings()` (a full corpus scan) before running the existing vectorized cosine/text-similarity check. This closes the gap the prior milestone left open: dedup *compute* was vectorized then, but the *I/O* feeding it (`_existing_chunk_embeddings()`) was still O(corpus) — that's fixed now.

**Problem 3 — Compliance metadata indexing.** `PostgresComplianceRepository.find_matching()` queries the composite index on `chunks(organization_id, legal_regulation, legal_authority, legal_jurisdiction, legal_article, legal_section, legal_clause)` — bounded by how many versions of one clause identity exist (typically single digits), not corpus size. `mark_superseded()` is a single indexed `UPDATE ... WHERE id = ?`. `IndexManager._detect_and_mark_superseded()` is otherwise unchanged logic, just calling the repository instead of `chunk_store.get_by_legal_metadata()`/`update_legal_metadata()`.

**Unified transaction boundary.** `IngestionUnitOfWork` still covers `documents` + `chunks` (document row + chunk rows written atomically, per the prior milestone). BM25 postings and compliance updates are **not** inside that same transaction — they're separate repository calls from `IndexManager`, same as `documents`/`chunks` were used standalone for *reads* in the pipeline. This is a deliberate, disclosed scope decision (see Trade-offs below), not an oversight.

## Repository architecture discipline

No new one-off modules. `BM25Repository` and `ComplianceRepository` are Protocols in `storage/repositories/base.py`, exactly like `DocumentRepository`/`ChunkRepository` from the prior milestone. `IndexManager` depends on the Protocols, never on `psycopg`, SQL, or which backend it received — `if postgres_dedup is not None`-style branching does not exist anywhere in this codebase. Every Postgres repository takes a `ConnectionProvider` (the shared pool, or a unit-of-work's fixed connection) and never opens its own connection. Scanning fallbacks (`storage/repositories/scanning/{bm25,compliance}_repository.py`) implement the identical Protocols, wrapping the exact prior full-scan/full-rebuild behavior, selected once in `api/dependencies.py`'s composition root.

## Comparison to production RAG systems

**Similar:** the write path (parse → chunk → dedup → embed → index) matches what Glean/Dropbox Dash/Notion AI do structurally — dedup and near-dup filtering before the expensive embedding/indexing work, incremental postings rather than batch reindex jobs, indexed metadata lookups instead of scans. LSH-banded SimHash for near-dup candidate generation is the same technique large-scale dedup pipelines use (e.g., web crawl dedup) before falling back to exact similarity computation on a narrowed set.

**Intentionally different:** production systems at OpenAI/Anthropic/Copilot scale typically run BM25/full-text search in a dedicated search engine (Elasticsearch/OpenSearch/Vespa) rather than hand-rolled SQL scoring — that's a valid future migration path once Postgres-based BM25 stops being sufficient, but implementing BM25-in-SQL first is the right sequencing here: it eliminates the audit's #1 and #2 ranked bottlenecks without adding new infrastructure, and the repository interface (`BM25Repository.search()`) is exactly the seam a future OpenSearch-backed implementation would slot into without touching `SparseRetriever` or `IndexManager`. Similarly, real LSH-based dedup at web scale uses MinHash + banding tuned against measured corpus statistics; this implementation's SimHash+banding constants (8×8) were tuned against two synthetic near-dup examples (documented in `hashing.py`'s docstring) — reasonable for this corpus's scale, explicitly flagged as revisit-if-scale-changes rather than a claimed-final tuning.

## Self-review

1. **Did I accidentally introduce any O(corpus) operations?** One was caught and fixed during implementation: `IndexManager.rebuild_bm25_index()` originally materialized `list(self.chunk_store.all())` *before* checking whether the backend needed it, which would have triggered a full Pinecone scan on every ingest even for the incremental Postgres backend — fixed by passing a lazy provider (`self.chunk_store.all`, uncalled) that the Postgres implementation's no-op `rebuild_full()` never invokes. Verified by a dedicated test (`test_postgres_backed_bm25_repository_never_triggers_full_corpus_scan`) using a chunk store that raises if `.all()` is ever called.
2. **Does every indexing operation now scale with the new upload?** Yes for the three problems in scope: exact-hash filtering (O(1) per hash), near-dup candidate narrowing (O(8) band lookups per chunk), BM25 postings (O(new chunks × avg terms/chunk)), compliance lookup (O(matching clause versions), not corpus size). Embedding and Pinecone upsert were already O(new chunks) from the prior audit.
3. **Can this realistically support millions of documents?** The per-operation complexity is right. The connection pool (`PostgresConnectionPool`, `min_size=1, max_size=10`) is a fixed small pool — fine for the single-worker ingestion path today, but will need tuning (and likely a queue/backpressure mechanism) once Problem 5's multi-worker queue lands and many workers share the pool concurrently. Not a blocker for this milestone; flagged for the next one.
4. **Can Problems 5 (Worker Queue) and 6 (Retrieval Pipeline) build on this without architectural changes?** Retrieval: yes, already partially done — `SparseRetriever` now accepts either `BM25Index` or a `BM25Repository` via a small structural Protocol (`retrieval/sparse.py`), and `api/dependencies.py` wires the Postgres-backed repository into it when configured, so BM25 search results reflect the incremental postings, not just the write path. Worker queue: yes structurally — `IngestionUnitOfWork`/`BM25Repository`/`ComplianceRepository` are all already safe to call from any thread/worker via the shared pool; Problem 5's `ingestion_jobs` table (already in the schema from the prior milestone) and a claim-based multi-worker loop can be added without touching `IngestionPipeline`'s or `IndexManager`'s public interfaces.

## Trade-offs (disclosed, not hidden)

- BM25 and compliance writes are not in the same transaction as the document/chunk writes. A crash between `IngestionUnitOfWork`'s commit and `IndexManager`'s subsequent BM25/compliance calls could leave BM25 postings or compliance flags briefly inconsistent with the chunk store. This mirrors the original code's behavior (BM25 rebuild and compliance detection were *already* separate steps after the chunk write, non-transactional) — not a regression, but also not the fully-unified single-transaction design the ingestion-flow diagram sketched. Unifying it would mean either merging `IndexManager` into the `IngestionUnitOfWork` boundary (a larger structural change affecting every `IndexManager` caller, including non-pipeline ones like the admin backfill script) or accepting a distributed-transaction-style reconciliation job — deferred as a explicit follow-up, not attempted under this milestone's scope.
- SimHash+banding constants (8 bands × 8 bits) are tuned against two synthetic examples, not a real corpus's measured near-dup rate. Documented in `hashing.py`; revisit if recall proves insufficient or the false-positive candidate rate proves too high at real scale.
- The pre-existing scan-cache bug in `PineconeChunkStore`/`PineconeVectorStore` (flagged in the prior milestone's PR) still blocks a handful of tests and the `scripts/benchmark.py` retrieval-quality script from running cleanly end-to-end in this environment. Not touched here — same scope boundary as before.
